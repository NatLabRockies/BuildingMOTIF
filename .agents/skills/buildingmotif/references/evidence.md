A repair proposal is a *hypothesis about the building*. This is how you test it against
what the user actually has: point lists, BACnet exports, control drawings, submittals,
sequences of operation, commissioning reports.

For a small corpus already available as files, start with a text search such as `rg`, then
read the surrounding source with the available file or shell tools.
Repair queries are narrow and targeted — "is there a zone temperature sensor for
VAV-1?" — and grep-first beats embeddings for this shape of question because the winning
evidence is often a *string*: a tag, a point name, or an equipment ID.

## 1. Build a text corpus

Work in the scratchpad; never write conversions into the user's project.

```bash
CORPUS=/tmp/.../scratchpad/corpus   # your session scratchpad
mkdir -p "$CORPUS"
```

| Source | Conversion |
|---|---|
| `.csv`, `.txt`, `.json`, `.ttl` | none — grep in place |
| `.xlsx` | `pandas.read_excel(path, sheet_name=None)` → write each sheet to CSV |
| `.pdf` | `pdftotext -layout file.pdf out.txt` (keep `-layout`: point-list tables lose their column structure without it) |
| `.docx` | `pandoc -t plain` |
| BACnet scan | already CSV/JSON via BuildingMOTIF's BACnet ingress |

Keep a mapping from each converted file back to its source path and page/sheet — you
must cite where evidence came from, and "I found it in the corpus" is not a citation.

## 2. Search around the gap

The gap gives you the search terms: the focus node's identifier and the class the hole
requires. For `bldg:VAV1` needing a `brick:Temperature_Sensor`:

```bash
# The equipment, across naming conventions — this is the money query
rg -i -n '\bVAV[-_ ]?0*1\b' "$CORPUS"

# Vocabulary for the required class, near the equipment
rg -i -n 'VAV.?1.*(temp|zn.?t|za.?t|room.?t)' "$CORPUS"
```

Building data is inconsistently named on purpose (by nobody). Vary aggressively:
`VAV-1`, `VAV_01`, `VAV 1`, `RM101_VAV`, `01-VAV-1`. Search the *abbreviations* a
building engineer would use, not the Brick class name — nobody writes
"Zone_Air_Temperature_Sensor" in a point list; they write `ZN-T`, `ZNT`, `ROOM_TEMP`,
`SPACE_TMP`.

Get the equipment's real-world tag first (from the model's labels, `rdfs:label`, or the
user), then search on *that*. Searching for `urn:bldg/vav1` in a submittal finds nothing.

## 3. Read the hit in context

Never map from a grep line alone. Read the surrounding rows: a point list's meaning
lives in its header row and its neighbours. `VAV1_ZN_T` beside a column marked `°F` and
`AI` is a zone temperature *sensor*; beside `AO` and a setpoint column it's a
*setpoint* — a different Brick class and a different repair.

## 4. Map evidence to the repair

Read the point's name, units, and I/O type together, then pick the Brick class:

- `AI` + `°F` + `ZN-T` → `brick:Zone_Air_Temperature_Sensor`
- `AO`/`AV` + `°F` + `ZN-SP` → `brick:Zone_Air_Temperature_Setpoint`
- `BO` + `START/STOP` → `brick:Start_Stop_Command`

Then bind the repair template's parameter to the **real identifier** from the document,
not a minted or autogenerated one:

```python
model.add_graph(t.evaluate({"repaired1": BLDG["VAV1_ZN_T"]}))
```

Prefer a *subclass* when the evidence supports it. A shape requiring
`brick:Temperature_Sensor` is satisfied by `brick:Zone_Air_Temperature_Sensor`, and the
more specific class is more useful downstream. The gate accepts it; reuse via the class
hierarchy is exactly what the monomorphism search is for.

## 5. Report evidence honestly

State what you found and how confident you are — the user is the one who knows the
building:

- **Direct hit** — "`points.csv:42` lists `VAV1_ZN_T` (AI, °F). Mapping it to
  `brick:Zone_Air_Temperature_Sensor` on VAV-1." Apply and cite.
- **Ambiguous** — several candidates, or the name does not disambiguate sensor versus
  setpoint → ask the user and include the actual document lines and consequences.
- **Nothing found** — say so. "No temperature point for VAV-1 in any document." Then ask
  whether the sensor exists (document is incomplete) or doesn't (the shape is too strict
  for this VAV). **Do not mint it on the theory that the shape requires it** — the shape
  requiring it is what's in question.

Absence of evidence is a real result and often the most useful thing you produce: it's
usually either a hole in the documentation or a wrong requirement, and both matter to the
user more than a silently patched graph.

## Scaling up

If grep genuinely fails — a large corpus where you can't guess the vocabulary — escalate
in this order before reaching for embeddings:

1. Dump the point list's distinct tokens/columns and read the naming convention off it;
   then grep with the convention. Most buildings have exactly one, and it's learnable
   from twenty rows.
2. BuildingMOTIF ships a **point label parser** for exactly this — the
   `buildingmotif.label_parsing` package (parser combinators: `string`, `regex`,
   `choice`, `sequence`, `constant`, `many`, `maybe`, `until`, `abbreviations`).
   `abbreviations({"VAV": BRICK.VAV, "ZN-T": BRICK.Zone_Air_Temperature_Sensor, ...})`
   expands building-specific tags to Brick classes; `sequence(...)` combines parsers
   into a naming convention. Output is a list of typed `TokenResult`s / token records
   you can turn into a model with a small graph-builder or template-binding step. This
   is the right tool for a whole-building point list. See `point_labels.md` in this skill,
   plus `docs/explanations/point-label-parsing.md`,
   `docs/guides/ingress-bacnet-to-brick.md`, and
   `notebooks/BMS_Point_Naming_Convention.ipynb` in the BuildingMOTIF repo.
3. Only if the corpus is large *and* unstructured prose (specs, O&M manuals) is semantic
   retrieval worth its dependencies — and ask the user before adding any.
